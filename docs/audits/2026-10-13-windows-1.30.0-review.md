## 2. “1 项失败”到底是谁的问题

### 2.1 Windows 路径断言：仓库测试缺陷，产品路径归一化正确

测试名：`APK project keeps extraction outside output and resumes with source fingerprint`。

位置：[ApkAndTechTests.cs:28](../../WC4MapEditor.Tests/ApkAndTechTests.cs#L28)、[fixture:251](../../WC4MapEditor.Tests/ApkAndTechTests.cs#L251)。fixture 使用：

```csharp
Path.Combine(Directory.GetCurrentDirectory(), "tmp/tests", Guid.NewGuid().ToString("N"))
```

在 Windows 上，这会留下混合的 `tmp/tests\...` 文本；产品用 `Path.GetFullPath` 得到规范的 `tmp\tests\...`。第 28 行用原始字符串 `==` 比较来源路径和默认输出路径，因此断言失败。第 35 行也存在同类比较，应一并核对。

| 单独验证 | 结果 |
|---|---|
| 输入 APK 原始字符串与 `SourcePath` 比较 | false |
| 双方先 `Path.GetFullPath` 再比较 | true |
| 预期输出原始字符串与 `OutputRoot` 比较 | false |
| 输出双方归一化后比较 | true |
| `IsApkSource` | true |
| 提取缓存与增量输出分离 | true |

进一步将该测试文件复制到临时验证项目，仅把 fixture 的 `"tmp/tests"` 改成两个路径段 `"tmp", "tests"`，**完整执行原测试剩余断言后通过**：包括新增表保存/恢复、来源保护、损坏缓存重建、缺失缓存资源重建、来源 APK 指纹变化拒绝。生产代码和仓库原测试未改。

因此准确归因是：**仓库测试存在 Windows 可移植性缺陷；原失败不证明 APK 功能失败；不能说与仓库代码完全无关，也不能说只是我的脚本问题。** PowerShell 将进程 stderr 包装成 `NativeCommandError`，只是日志展示形式；异常堆栈仍指向仓库测试第 28 行。

建议：fixture 用独立路径段；路径断言双方归一化并使用符合平台的比较规则。保留全部行为断言，避免仅放宽条件把真实路径错误也放过。

### 2.2 本次新增失败：本机缺少原始 APK

测试名：`real 1.30.0 APK opens all project resources with incremental HQ and steel-flood edits`。

[ApkAndTechTests.cs:159](../../WC4MapEditor.Tests/ApkAndTechTests.cs#L159) 固定读取 `G:\document\githup\game\wc4\World Conqueror 4_1.30.0.apk`；本机只有指定的解包目录，缺少这个 APK。失败发生在第 160 行 `File.ReadAllBytes`，尚未进入产品加载流程。

## 4. 已复现的程序与发布问题

### R01 / P1：外部地形关卡缺少对象坐标转换

相关位置：[ProjectMapDocument.cs:63](../../WC4MapEditor.Core/Assets/ProjectMapDocument.cs#L63)、[BuildingRender.cs:253](../../WC4MapEditor.Rendering/Skia/BuildingRender.cs#L253)、[ArmyRender.cs:550](../../WC4MapEditor.Rendering/Skia/ArmyRender.cs#L550)、[BuildingModifier.cs:24](../../WC4MapEditor.Core/Modifiers/BuildingModifier.cs#L24)。

`ProjectMapDocument` 根据 `MapClipX/Y` 从 `world.bin` 取出本地地形，但对象仍保留源 BTL 的世界索引。渲染器按 `coordinate / map.MapWidth` 和 `% map.MapWidth` 换算，错误地使用本地窗口宽度。

真实样本 `stage10001.btl`：`MapNumber=1`、窗口 `12×10`、capture `(33,5)`，world 宽为 148。第一座建筑原索引 784，正确世界坐标为 `(44,5)`，窗口坐标应为 `(11,0)`；当前计算为 `(4,65)`，越过本地高度 10，因此不显示。该文件的 11 个建筑、18 个部队全部如此，实际 WPF 单位/建筑模式看到地形而没有这些对象。

| 310 张外部关卡统计 | 建筑 | 部署部队 |
|---|---:|---:|
| 总记录 | 5,988 | 15,617 |
| 按当前本地面积判断会越界 | 2,450 | 9,014 |
| 按世界宽度及 capture 换算后落在本地窗口 | 5,988 | 15,617 |

全部 310 张均至少含一个按当前逻辑越界的对象。未越界的剩余记录也不能视为位置正确：例如 `conquest1.btl` 的世界索引 348 应映射到窗口 `(52,0)`，直接除以 148 得到 `(52,2)`，Y 偏移未扣除。上述统计只覆盖建筑和已部署部队，未擅自套用于未确认格式的援军、事件、opaque 区段。

源数据在世界坐标体系下全部能落入 capture，这应归为**编辑器适配缺陷**。旧 [项目说明第 4.4 节](../projects/wc4-1.30.0/README.md#44-capture坐标与关联文件) 中“BTL 内对象使用其本地窗口坐标”的陈述被本次数据推翻，应以本报告的实测为准。

建议：建立统一的原始坐标 ↔ 本地视图坐标转换层；`MapNumber=0` 继续使用本地索引，`MapNumber=1` 使用来源 world 宽度和 capture。参考换算：

```text
worldCol = rawIndex % worldWidth
worldRow = rawIndex / worldWidth
localCol = (worldCol - MapClipX + worldWidth) % worldWidth
localRow = worldRow - MapClipY

rawIndex = (MapClipY + localRow) * worldWidth
         + (MapClipX + localCol) % worldWidth
```

渲染、点击选取、列表、修改器、新增/移动对象、命令、保存都要使用同一规则；不要直接把所有记录重写成本地坐标破坏现有无修改保存的保真。当前新增建筑使用 `row * localWidth + col`，因此外部关卡的编辑写回还有坐标错误风险；本次未把这类输出打包到 Android 验证。

验收：`stage10001`、`conquest1`、跨右边界 `stage60023`、奇数 X 的 capture 和本地 `stage10004` 同时覆盖；对象落点/点击一致，新增/移动后反向转换正确，未改动记录字节保持一致。省份首都引用、归属读写和六边格奇偶列锚点也需同步核对。

### R02 / P1：建筑覆盖撤销丢原数据，重做受后来复制影响

相关位置：[BuildingDeployMode.cs:98](../../WC4MapEditor.Core/Mode/BuildingDeployMode.cs#L98)、[BuildingDeployMode.cs:179](../../WC4MapEditor.Core/Mode/BuildingDeployMode.cs#L179)、[BuildingModifier.cs:188](../../WC4MapEditor.Core/Modifiers/BuildingModifier.cs#L188)。

在真实 `stage10004.btl` 上通过生产 `EditModeManager.HandleKeyAction` 重现：

| 触发步骤 | 实际结果 | 预期 |
|---|---|---|
| C 复制一座建筑，V 覆盖另一座，撤销 | 原目标建筑消失，`presentAfterUndo=false` | 恢复原目标完整记录和归属 |
| 对已有建筑执行 `apply`，撤销 | 原建筑消失 | 恢复覆盖前数据 |
| 新会话剪贴板为空，对已有建筑 V，再撤销 | V 返回 true，记录 1 条历史；撤销删除原建筑 | 粘贴失败，数据/dirty/历史都不变 |
| 粘贴类型 11，撤销；再复制类型 15，重做 | 重做变成类型 15 | 重做恢复首次粘贴的类型 11 |

原因：覆盖前只取了归属值；undo 固定调用 `Remove`。execute 忽略 `PasteBuilding` 的失败返回值，并把 redo 留成再次读取当前剪贴板的闭包。

建议：先验证操作成功条件，再捕获目标旧建筑/旧归属及独立复制的候选新建筑，命令持有确定的 before/after；覆盖与新建的 undo 区分处理，失败不登记历史，不修改其他字段。

验收：覆盖、空目标、空剪贴板、不可写坐标、undo 后更换剪贴板再 redo；完整 32 字节建筑字段与归属都可恢复，失败时历史计数不增。

### R03 / P1：等级与多选粘贴没有撤销记录

位置：[BuildingDeployMode.cs:156](../../WC4MapEditor.Core/Mode/BuildingDeployMode.cs#L156)、[BuildingDeployMode.cs:172](../../WC4MapEditor.Core/Mode/BuildingDeployMode.cs#L172)。

真实关卡中等级粘贴把工厂等级从 0 改为 7，但 `UndoCount=0`、`Undo=false`、`DataModified` 通知次数为 0；地图的 `IsModified=true`，不能因此误报为完全没有脏标记。多选粘贴把建筑数从 6 改为 8，也没有历史，只有一次修改通知。

两个分支直接调用修改器后返回，绕过普通粘贴使用的命令记录。建议单建筑等级使用固定 before/after 命令，多选使用一个批量命令或现有 `RecordBuildingsSnapshot`，操作成功后统一通知。批量计数还应只累计 `Apply.Success`，不能无条件 `count++`。

验收：等级/多选一次撤销恢复完整建筑集合，重做不依赖剪贴板，越界或部分失败的处理与实际修改数量一致。

### R04 / P1：复制等级没有清除上一次建筑组

位置：[BuildingModifier.cs:168](../../WC4MapEditor.Core/Modifiers/BuildingModifier.cs#L168)、[BuildingDeployMode.cs:156](../../WC4MapEditor.Core/Mode/BuildingDeployMode.cs#L156)。

复现：多选复制两座建筑 → 清除选区 → Ctrl+C 仅复制一座建筑的等级 → 对空格子 V。实际粘贴成功并增加两座建筑，`HasCopiedGroup=true`；正确行为应提示空格子没有建筑，不能贴等级。

原因：`CopyBuildingLevels` 更新 `_copiedBuilding`，没有清空 `_copiedBuildingGroup`；paste 先检查组，后检查等级标志。

建议：剪贴板用明确的 `Empty / Single / Levels / Group` 状态，每次成功复制原子替换内容。消除 Mode/Modifier 重复状态；失败复制是否保留旧内容也应有一致约定并显示提示。

### R07 / P2：重复扫描使加载和返回首页明显停顿

位置：[GameProjectDataSession.cs:26](../../WC4MapEditor.Core/Assets/GameProjectDataSession.cs#L26)、[BeginScene.Project.cs:144](../../Views/BeginScene.Project.cs#L144)、[AssetCache.cs:304](../../WC4MapEditor.Core/Assets/AssetCache.cs#L304)。

第一轮 GUI 的 7 次全量扫描日志为 `7882、7279、9795、8535、7977、7835、10363 ms`，每次都是同一个 3,474 文件项目；合计扫描 59.7 秒，均值 8.52 秒。它们发生在激活及数次返回首页，期间没有项目资源编辑；计时是扫描内部时间，不是所有交互耗时。

激活已经扫描，首页构建又 `forceReload:true`；每次返回首页也同步执行。扫描还提升 revision，使相关图集缓存失效，进一步增加后续重建成本。首轮初始加载至少有两次约 7–8 秒扫描。磁盘、安全检查和缓存温度会影响绝对时间，重复扫描的调用结构则是确定的。

建议先移除展示首页时的无条件刷新，通过当前 root/revision 重用索引；显式刷新才全量扫描。保存后按受影响文件刷新目录和解析缓存，仍保留外部文件变更检测；首次扫描放后台并显示真实进度及取消状态。之后再测路径解析/链接检查等逐文件热点，避免未经分析删除源保护逻辑。

验收：没有资源修改时返回首页不出现新扫描、不让 revision 无故变化；打开项目只建立一次完整索引；外部改表及新增输出仍能在刷新后生效。

### R08 / P2：OCR 外部依赖没有随最新源码提供

位置：[ExternalToolRunner.cs:15](../../WC4MapEditor.Core/Services/ExternalToolRunner.cs#L15)、[RenderSceneBase.cs:3722](../../Views/RenderSceneBase.cs#L3722)。

需要 `Lib/ocr_map.exe` 和 `Lib/gen_buildings_zme.exe`；当前源码没有 `WC4MapEditor.Core/Lib`，当前 13 文件发布包也没有这两个工具。生产可用性检查返回 `IsOcrAvailable=false`、`IsGenBuildingsAvailable=false`。建筑模式 P 键会在执行 OCR 前提示缺少工具。

这不是警告导致，也不是仅发生在目标游戏目录中。项目文件已有复制规则，但输入工具不存在时，构建仍成功；因此干净 checkout 无法复现注释中“工具随程序输出”的能力。

建议明确它们是必需发布依赖还是可选扩展：前者需要受控版本、下载/构建方式、校验及打包断言；后者应在界面显示不可用原因及安装位置。验收以干净源码生成的包实际跑一次离线 OCR 为准，而不只检查文件名。

### R09 / P2：超范围建筑名称 ID 被截断

位置：[BuildingNameResolver.cs:37](../../WC4MapEditor.Core/Services/BuildingNameResolver.cs#L37)。

`ushort.TryParse` 失败后，只要 `int.TryParse` 成功就 `unchecked((ushort)signed)`。实测 `Resolve("65536")=0`、`Resolve("-2")=65534`；这会把用户输错的 ID 静默变为另一名称或无名。

建议仅将明确约定的 `-1` 映射为 `0xFFFF`，其他数值限制在 0..65535，超范围报告字段错误并保留编辑值。GUI、CLI、脚本调用同一校验规则。验收覆盖 -2、-1、0、65535、65536 和大整数。

### R10 / P2：布局实体会被再次转义

位置：[LayoutDocument.cs:174](../../WC4MapEditor.Core/Parsers/Layout/LayoutDocument.cs#L174)、[LayoutDocument.cs:205](../../WC4MapEditor.Core/Parsers/Layout/LayoutDocument.cs#L205)。

宽松解析器保留属性原文本，未把实体解码；Dump 对 `&` 再转义。复现输入 `text="A &amp; B"`，只改 Form 宽度后保存，输出变成 `text="A &amp;amp; B"`。标准 XML 读取值由 `A & B` 变为 `A &amp; B`，语义改变。

当前目标的 `layout.xml` / `layout_x.xml` 没检出 XML 实体，因此这次原始加载不触发该问题；用户导入布局或新增含特殊字符的文本后可触发。建议保留宽松语法兼容的同时正确解码实体，保存只转义一次。补属性/文本、数值实体、特殊符号及连续两次保存的语义稳定测试；不要用仅“能再次解析”的测试代替保真。

### R11 / P2：关系诊断缺少版本与记录类型语义

位置：[AssetRelationshipAnalyzer.cs:334](../../WC4MapEditor.Core/Analyzers/AssetRelationshipAnalyzer.cs#L334)。具体来源数据见第 6 节。

当前规则直接比较 `Skills.Count > SkillsMax`。目标项目有 1,062 条 `Type=3` 记录，其 `SkillsMax=0` 但已有技能；全部被记为 error，界面/CLI 因此长期呈现大量错误并返回非零。

证据说明这是稳定的记录类型差异，尚不足以证明 `SkillsMax=0` 在游戏中一定等于“不允许已有技能”。建议按游戏版本和记录类型建立规则，语义未确定的约束归为待核实，真正缺失引用、重复 ID 和格式错误单独显示；不要自动清空技能让检查归零。

## 5. 需要继续验证的草稿与生命周期风险

以下没有混入“普通用户操作已复现”的列表。

### 5.1 通用 JSON 保存会丢弃全局字符串草稿

[JsonTableEditScene.cs:253](../../Views/JsonTableEditScene.cs#L253) 在保存修改表后调用全局 `ReloadEditors`；[ConfigManager.cs:673](../../WC4MapEditor.Core/Config/ConfigManager.cs#L673) 的 Reload 将 `_stringTableParser=null`。

核心复现：让 `ConfigManager.GetStringTableParser()` 持有未保存条目 → 保存另一 JSON → 调用界面同一刷新方法。旧 parser 仍 dirty，但新的活动 parser 不含条目，磁盘也没有字符串覆盖文件。

这确认了全局刷新不保留该种草稿的行为，但本次**没有串联出普通 GUI 必然丢稿的完整路径**。当前主窗口离开多数专用编辑器有未保存确认，`BuildingNameResolver` 的正常命名路径会即时保存，不能直接把这一核心探针结果等同于“每次切换编辑器都会丢数据”。建议变更刷新按资源定位，并明确会话持有的草稿所有权；再补“缓存地图/专用表/字符串编辑后打开另一张表保存”的联合用例。

### 5.2 内存与缓存需要测量，尚无泄漏结论

初始项目加载约 231 MiB；连续打开将领、总部、94 图集布局、三个地图后，采样工作集达到约 636 MiB，后续 PKM 阶段约 554 MiB。工作集受场景保留、Skia 解码缓存和 GC 影响，单次顺序采样不能证明内存泄漏。

建议在处理 R07 后，针对反复打开/关闭同一编辑器、地图切换、主动释放及大图导入测量受管堆与原生位图，验证 scene/history/cache 的预算与 Dispose 所有权。无需根据一次工作集值贸然清掉所有缓存。
