## 1. 警告的含义与处理

### 编译警告

原 Windows 报告的 41 条警告为 34 条可空引用警告、7 条未使用成员警告。远端最新版已修复；本轮主程序和测试工程的 Release 构建均为 **0 错误 / 0 警告**，没有新增编译警告屏蔽项。历史报告与警告 CSV 保留原状，不能再把其数量当作当前结果。

### PNG 的 `iCCP: known incorrect sRGB profile`

10 月 15 日包的 GUI stderr 留有两条该提示。它表示 PNG 的嵌入色彩配置有已知问题，图片仍可解码，和 C# 编译警告、地图数据校验错误不同。

只读扫描真实项目发现 **37 张 PNG** 携带同一份 3,144 字节的旧配置：HP-Microsoft sRGB v2 perceptual。其 Adler-32 为 `f784f3fb`，SHA-256 为 `2b3aa1645779a9e634744faf9b01e9102b0c9b88fd6deced7934df86b949af7e`。libpng 1.6.43 的 [已知配置列表](https://github.com/pnggroup/libpng/blob/v1.6.43/png.c#L2269)明确将其标记为 broken；问题在白点等配置元数据。PNG chunk CRC 本身正确，不表示图片像素损坏。

涉及 `image_boundary.png`、`image_boundary@2x.png`、`image_line.png`、`image_line@2x.png`、`image/tex_bg_glory.png`、`image/elite/218.png`、`image/event/806.png`，以及 `image/wonder_icon/wonder_101.png` 至 `wonder_130.png`。

修复见 [PngColorProfile](../../WC4MapEditor.Rendering/Imaging/PngColorProfile.cs)和[共享解码入口](../../WC4MapEditor.Rendering/Imaging/ProjectImageDecoder.cs)：

- 仅在解码副本内，将解压长度、SHA-256 和 chunk CRC 全部匹配的这一种 iCCP 替换为标准 sRGB 标记，保持其 perceptual intent。
- 保留 IDAT 和其他数据块；来源文件、编辑器持有的原始编码字节不变，无改动保存返回原字节。
- 正常线性色彩配置、未知 ICC、非 PNG、损坏 CRC、截断或重复配置交由原解码器处理，不批量剥离 ICC，也不重定向或屏蔽 stderr。
- 限制压缩块大小和解压读取量，避免为识别配置而无界分配内存。图片编辑、图集编辑、位图字体、调试背景与视图层使用相同的兼容处理。

这里需要保留标准 sRGB 标记。仅删除 iCCP 时，`tex_bg_glory.png` 会被剩余元数据解释为不同色彩空间。当前回归验证 37 张图的尺寸、像素格式、透明度、色彩空间和逐字节像素均与修复前一致，且无改动保存保留原编码。

证据边界：本轮旧包的启动、加载、地图、将领及技能入口未稳定重现历史两条 stderr，单独解码全部 1,677 张图片也无该提示。因此不能逐条断言历史两次来自哪两张图，也不能把桌面组件与渲染核心版本差异当作已证实根因。实际原生 `libSkiaSharp.dll` SHA-256 在桌面包与测试探针中相同。修复针对已确认的无效色彩配置，并以像素及保存保真测试约束行为。

### 建筑可选图集的“加载失败”

旧日志在 `buildings_hd` 已正常生成 36 个建筑、6 个设施、5 个等级纹理时，还会输出 `加载 buildings 失败: 项目缺少图集：buildings.xml`。原因是查找不存在的建筑变体时探测旧版可选回退图集。

[HdAtlasParser.GetOptional](../../WC4MapEditor.Core/Parsers/HdAtlas/HdAtlasParser.cs)现区分“可选 XML 不存在”和“已有 XML 损坏/缺纹理”；[ProjectSpriteLoader](../../WC4MapEditor.Rendering/Imaging/ProjectSpriteLoader.cs)仅对次选图集采用该探测，并按资源 Revision 缓存缺失结果，避免数百次重复查盘。首选图集缺失、回退 XML 损坏和缺纹理仍有诊断，保存覆盖后会重新发现资源。

## 4. 编辑页最大化与统一窗口控制

用户实际反馈是进入某个修改项之后无法主动全屏。代码中首页和地图页各自带有窗口控制，将领、技能、国家、配置表等编辑页却没有最大化按钮。窗口进入这些页面后没有统一的窗口操作入口。初次按 92% 工作区放大启动尺寸没有解决这个问题，该行为已撤回，最终版本仍以 **1250×700、普通窗口、居中** 启动，最小尺寸维持 760×520。

本次将最小化、最大化/还原、关闭移至主窗口公共标题栏，所有编辑页共享；原首页和地图页的重复窗口按钮移除。标题栏独占布局行，避免覆盖编辑工具栏。用户可点击右上角的最大化按钮、双击标题栏，或按 **F11** 在最大化与普通窗口之间切换；再次切换会还原之前的窗口大小。输入框内也可使用 F11，对话框覆盖层打开时则保留其模态输入行为。

最大化去掉外围 10px 留白和阴影，场景宿主按剩余区域拉伸；切换编辑项不会重置最大化状态。无边框窗口的 `WM_GETMINMAXINFO` 根据当前显示器的工作区计算展开位置和尺寸，任务栏仍可使用；最大化时不启用边缘拖拽缩放，普通窗口仍可拖动缩放。也修复屏幕负坐标的边缘命中计算，适配放在主屏左侧或上方的显示器。

启动位置与透明度动画继续使用 `FillBehavior.Stop`，避免完成后仍由动画终值控制窗口位置。

本机以独立 STA 后台检查了实际窗口和 **12 个页面**：首页、资源浏览器、将领、技能、国家、兵种、建筑、国家科技、通用 JSON/总部科技、文本、布局和战役地图。逐页检查了公共按钮点击、最大化内容拉伸和还原为 1250×700；另验证 F11、模态覆盖层、最大化后切换页面和原生工作区消息处理。1536×864 的 WPF 工作区下，公共标题栏高 36、场景内容为 1536×828；原生工作区返回 1920×1080，对应本机显示缩放。全部通过，构建为 0 警告 / 0 错误。

检查未调用主窗口 `Show()`，没有抢占焦点或移动鼠标，`IsVisible=false`、`Topmost=false`；此结果仍不替代各 DPI/多屏下的实屏视觉验收。

实现见 [MainWindow.xaml.cs](../../Views/MainWindow.xaml.cs)、[BeginScene.xaml.cs](../../Views/BeginScene.xaml.cs) 和 [RenderSceneBase](../../Views/RenderSceneBase.cs)。
